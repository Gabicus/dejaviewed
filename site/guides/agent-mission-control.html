Mission Control for 80 Agents — Conway's law meets game UI

Insight class: Creative Fusion · Difficulty: Experimental · Quality: 3/5 Connected entries: 11 · Tools: AgentCraft, Arize, BigQuery, Bot Crossing, ChatGPT, Claude, Claude Code, Founder OS, Ghostty, Kafka, Mac Mini, Meta Quest 3, Minecraft, Slack, TouchDesigner, Trackio, git, tmux

Thesis

Once you run more than a handful of agents, the bottleneck is your attention, not tokens. Creative technologists are already prototyping the answer without naming it — Bot Crossing puts 80 agents on a tiny planet where they raise hands for help, AgentCraft runs them as Minecraft workers in isolated worktrees, a TouchDesigner sketch commands agents by gesture, a Quest 3 canvas directs them spatially. Casey Muratori's point that Conway's law now applies to agents says the interface and the agent org chart are the same design problem. Feed a Booking.com-style trace bus into a game-engine front end and you get a control room where structure is visible.

Why it matters

Solo operators running Founder-OS-style setups spend their day polling terminals. A spatial view that surfaces only blocked agents, and whose layout mirrors how work is partitioned, lets one person supervise ten times more agents without reading every log.

Action sketch — how to implement this

Emit one JSON event per agent state change (started, blocked, needs-review, done) from your harness hooks onto a local queue — Redis or a file tail is enough to start

Point Bot Crossing (or a 200-line Three.js scene) at that queue so blocked agents visibly raise hands; cluster agents by the repo/module they own to make the Conway structure visible

Run a week with dashboard versus without and log minutes-to-unblock per blocked agent

Falsifier: if minutes-to-unblock does not drop by at least a third versus a plain notification, the game layer is decoration and a notch widget wins

Prerequisites

A multi-agent setup with hooks

Basic Three.js or TouchDesigner

Willingness to treat this as an art-tech experiment first
