Boris Cherny's CLAUDE.md — The Canonical Template

Author of the pattern: Boris Cherny — Anthropic staff engineer, creator of Claude Code (originally built as a side project in his first month at Anthropic; by the time Claude Code launched publicly in May 2025, over 80% of Anthropic's engineers were using it daily).

Why it matters: Boris's own CLAUDE.md and the workflow rules he published on X became the de facto template that the wider community now cargo-cults. If you've seen a CLAUDE.md with sections like "Workflow Orchestration," "Self-Improvement Loop," and "Verification Before Done," you're looking at a descendant of Boris's file. His team at Anthropic keeps a CLAUDE.md in git at roughly 2.5k tokens — the reference weight class.

This guide reconstructs the template, explains why each section exists, and compares it to a real-world global CLAUDE.md setup.

What it is

CLAUDE.md is the single highest-leverage file in the Claude Code harness. Claude Code injects it into the context window at the start of every session, before the user's first message. It's the only persistent memory primitive that survives compaction, resumes, and cross-session restarts. Nothing else — not chat history, not subagent output, not tool results — is guaranteed to stick.

Boris's core insight: CLAUDE.md is a compounding asset. Every correction you give Claude should be distilled into a rule in CLAUDE.md, so future sessions never make the same mistake twice. The file is not documentation for humans — it is a behavioral contract for the model.

How it works under the hood

Claude Code auto-discovers ./CLAUDE.md (project), ~/.claude/CLAUDE.md (global), and .claude/CLAUDE.md in parent dirs (walks up the tree).

All discovered files are concatenated and prepended to the system prompt.

/init scaffolds a starter CLAUDE.md by scanning the project (language, framework, build/test commands, style).

# prefix in a normal Claude message auto-appends that line to CLAUDE.md — Boris's favorite shortcut for the self-improvement loop.

Target weight: under 200 lines / under 2-3k tokens. Larger files measurably reduce instruction adherence — Claude starts "forgetting" rules buried mid-file.

Key mechanics (Boris's rules, annotated)

Boris's publicly posted rules crystallize into these sections. The exact wording varies by gist (there are at least four circulating community copies), but the structure is consistent:

1. Workflow Orchestration — "Plan first, execute second"

Workflow

For any non-trivial task (3+ steps or architectural decisions), enter plan mode first.

Write the plan to disk before executing. Get explicit approval before you start editing files.

Break work into phases. Each phase ends with a verification step.

Never start coding without a written goal and a verification strategy.

Why: Claude's default behavior is to dive in. Forcing a written plan makes the model's reasoning visible, lets the human catch bad assumptions cheaply, and creates a contract it can check itself against later. This is the pattern the Superpowers writing-plans + executing-plans chain formalizes.

2. Subagents — "Keep the main context clean"

Subagents

Use subagents liberally. The main conversation is a precious resource.

Dispatch anything exploratory (searching, reading unknown files, running tests) to a subagent.

Subagents return summaries, not transcripts. You don't burn tokens on the tool noise.

Parallelize independent tasks — spawn 3-5 subagents at once rather than serially.

Why: The main context window is where the actual planning and decision-making happens. Every file you read, every failed test output, every grep result eats tokens that could be used for reasoning. Subagents are a context-compression mechanism.

3. Verification Before Done — "Never claim completion without proof"

Verification

Before claiming any task is complete: run the tests, run the linter, run the type checker.

If the user's request implies "it should work" — prove it works end-to-end, don't just compile.

If you wrote a function, write a test. If you wrote a test, run it. If it fails, fix it.

Never say "done" if you haven't verified. Say "I believe this is done pending X."

Why: The single most common failure mode of LLMs is confident false completion. Boris's rule: the model must produce evidence, not assertion.

4. Self-Improvement Loop — "Every correction becomes a rule"

Self-Improvement

When I correct you, end your response with:

"Updating CLAUDE.md so I don't make this mistake again."

Then actually update CLAUDE.md with a new rule that would have prevented the mistake.

Ruthlessly edit CLAUDE.md over time. Delete rules that no longer apply. Merge duplicates.

Why: This is the compounding mechanism. Boris's own quote: "Invest in your CLAUDE.md. After every correction, end with 'Update your CLAUDE.md so you don't make that mistake again.' Claude is effective at writing rules for itself." Over weeks, Claude's mistake rate on your codebase measurably drops.

5. Autonomous Bug Fixing — "Reproduce, then fix"

Bugs

Before fixing: reproduce the bug with a failing test.

The test must fail for the right reason (the bug), not a different reason (typo, missing import).

Only then write the fix. Re-run the test. Confirm it passes. Run the full suite.

If the bug is ambiguous, ask for clarification before coding.

Why: Mirrors TDD discipline and cuts the "fixed something unrelated" failure mode.

6. Project context (the boilerplate head of the file)

Project Name

Language: Python 3.12 Framework: FastAPI + SQLAlchemy Package manager: uv Tests: pytest (run with uv run pytest) Lint: ruff (run with uv run ruff check) Typecheck: mypy (strict mode)

Conventions

Prefer dataclasses over dicts for structured data.

All public functions get type hints.

Never use print — use the logging module.

Tests live in tests/ mirroring src/ layout.

Why: This is the cheap, obvious part everyone gets right. It's the behavioral rules above that distinguish Boris's template from a README.

Contrast with a global CLAUDE.md

A production global CLAUDE.md (~/.claude/CLAUDE.md) is a fundamentally different genre than Boris's per-project file. Key differences worth understanding:

Dimension Boris's template Global orchestrator

Scope Per-project behavioral contract Global meta-orchestrator across ALL projects Length ~200 lines, ~2.5k tokens ~250 lines but dense with tables Focus Workflow discipline (plan → execute → verify) Skill routing + knowledge base pointers Self-improvement loop Yes — "every correction becomes a rule" Implicit via forge/retro/flywheel skills Trigger mapping Not present Extensive — keyword → skill table Domain knowledge Project-specific conventions AI3 resource catalog, installed plugins/MCPs Security rules Not present Top-level CRITICAL block on secret protection

What a global file does that Boris's doesn't:

Maps user trigger words to specific skill invocations (Boris has no skills system at his abstraction level).

Treats the knowledge flywheel (/flywheel, /forge, /inject) as default-on.

Enumerates the installed plugin/MCP inventory so Claude knows what tools exist.

Points to an external resource catalog (ai3-resources/) that the agent can cross-reference.

What Boris's file does that a global file typically doesn't:

Explicit plan-mode gating for non-trivial tasks.

Explicit verification-before-done discipline (a global file may delegate this to a verification-before-completion superpower).

The self-improvement loop as a first-class mechanic ("every correction becomes a rule").

Lean, project-specific behavioral rules with teeth.

The gap to close: A global CLAUDE.md can be excellent at orchestration but light on direct behavioral discipline — relying on the skill layer to enforce plan mode, TDD, and verification. Boris's pattern pushes that discipline directly into the file so it's enforced even in lightweight sessions where no skill was explicitly invoked. A hybrid per-project CLAUDE.md that inherits global triggers and adds a Boris-style Workflow/Verification/Self-improvement block would capture both.

Gotchas

Length creep kills adherence. Past ~300 lines, Claude starts ignoring rules in the middle of the file. Ruthlessly prune.

CLAUDE.md is not documentation. Don't write prose, write rules. "The foo module does X" is dead weight; "Always use the foo module's safe_parse, never parse" is a rule with teeth.

Rules without teeth are ignored. "Prefer X" is weaker than "Never Y." Boris's negative-constraint framing ("NEVER commit with --no-verify") works because it names the exact failure mode.

The self-improvement loop only works if you actually run it. The discipline is: every time you correct Claude, ask it to update CLAUDE.md. If you skip that step once, the loop is broken.

Global + project files concatenate. Don't repeat global rules in every project file — Claude reads both.

Community gists are not canonical. There are at least four different "Boris's CLAUDE.md" gists circulating. They agree on structure but differ on wording. Treat them all as reference, not gospel.

What we could build with it

A per-project CLAUDE.md generator that fuses global orchestration rules with Boris's behavioral discipline blocks, auto-populated from project introspection (stack detection, test/lint commands).

A CLAUDE.md linter that flags length creep, rule duplication, weak positive framing, and un-earned rules (rules without git blame showing a corresponding correction).

A self-improvement loop hook — a PostToolUse hook that detects user corrections in the transcript and prompts Claude to propose a CLAUDE.md diff.

A rule-provenance tracker — every rule in CLAUDE.md links back to the commit/conversation that introduced it, so stale rules can be pruned with evidence.

3 · Step-by-step prompts

Step 1 — Ground truth: docs, version, current file

Goal: Know how this Claude Code version loads memory and what the project file says now.

Run claude --version and record it. Read the official Claude Code docs for memory, settings, hooks, slash commands and headless mode for this version. Check each guide claim and write claims.md with verified, outdated or unverified plus the doc URL: discovery locations (project root, ~/.claude/CLAUDE.md, parent directories, nested subdirectories, any local or imported files); whether contents are prepended to the system prompt or injected another way; whether the # shortcut still appends to memory; whether /init and /memory behave as described; whether any doc states a size guideline; the 80% daily-use figure and its source. In a live session run /memory and record which files are loaded for this project. Copy the project's current CLAUDE.md to CLAUDE.old.md. Count lines and tokens for it, and list every command it names; run each command once and record whether it works.

Expect: claims.md, loaded_memory.md, CLAUDE.old.md, a command check table.

Audit before moving on: Every claim cites a doc URL or a test you ran. Any command in the old file that fails is marked for fixing in the new file.

Step 2 — Mine corrections

Goal: Find the mistakes that actually repeat in this project.

Search git log messages and diffs for reverts, 'fix' commits following agent commits, and edits to CLAUDE.md, and list what each was correcting. Search the project's Claude Code session transcripts (in the user's Claude projects directory for this repo) for user messages that correct the agent: phrases like 'no', 'wrong', 'don't', 'I told you', 'again', 'you broke'. Do not copy secrets or personal data from transcripts; quote only the correction gist. Group corrections into themes (wrong command, claimed done without tests, edited the wrong file, ignored plan, touched production, verbose output). Count occurrences and note the last date. For each theme, decide whether it needs a CLAUDE.md rule, a hook, a permission setting, or nothing (one-off). Prefer a hook whenever the violation is detectable from the tool input alone, such as a command string or a file path.

Expect: corrections.md with themes, counts, dates and the proposed mechanism for each.

Audit before moving on: Each theme has at least one cited commit hash or transcript date. Themes seen once in more than a month are marked one-off unless they caused damage.

Step 3 — Draft the new CLAUDE.md

Goal: Write a lean file where every rule earns its place.

Write CLAUDE.md using Boris's structure, adapted to this project:

Head: project one-liner, stack, and the exact build, test, lint and typecheck commands taken from the project's config and verified in step 1.

Workflow: plan mode and a written plan for tasks with 3 or more steps or architectural choices.

Subagents: use them for exploration and parallel independent tasks; they return summaries.

Verification: never claim done without running the test, lint and typecheck commands; say what was not verified.

Bugs: reproduce with a failing test that fails for the right reason before fixing.

Self-improvement: when corrected, propose a rule; delete rules that no longer apply.

Project rules from corrections.md that chose the 'rule' mechanism, each with a short reason.

Put the most violated rules near the top. Keep it under 200 lines and 3k tokens; measure both. Write a diff against CLAUDE.old.md and list removed rules with the reason for removal.

Expect: CLAUDE.md, a diff, a removed-rules list, line and token counts.

Audit before moving on: Any rule without a reason or incident is removed or justified. If the file exceeds limits, cut conventions the linter already enforces first.

Step 4 — Hooks for absolute rules

Goal: Make the rules that must never break deterministic.

For each theme in corrections.md that chose 'hook' or 'permission', and for standard absolute rules (no secrets in commits, no force push, no push to main, no destructive deletes at repo root), write enforcement in .claude/settings.json: permission deny rules where a pattern suffices, and PreToolUse hooks running a small script that inspects the tool input and exits with a blocking status and a message when it matches. Keep hook scripts in .claude/hooks/ with tests: feed each script a sample violating and a sample allowed tool input and assert the exit code. In a live session, deliberately ask Claude to perform each blocked action and confirm the hook blocks it with a clear message. Remove the matching prose rule from CLAUDE.md or shorten it to a pointer to the hook.

Expect: .claude/settings.json, .claude/hooks/ with tests, a live-block log.

Audit before moving on: Every hook test passes and every live attempt is blocked. A hook that blocks legitimate work in normal use is narrowed before moving on.

Step 5 — Build and run the behavioural eval

Goal: Measure whether the file changes behaviour.

Create eval/tasks/ with at least 12 tasks, each a small, real change in this repo designed to tempt one rule: a bug fix that invites patching without a failing test; a 4-step feature that invites skipping a plan; a change where the wrong package manager command is tempting; a task that ends with an easy chance to claim done without tests. Write eval/run.sh: for each arm (no CLAUDE.md, CLAUDE.old.md, new CLAUDE.md), for each task, 3 runs, in a fresh git worktree, run claude -p with the task prompt and --output-format json, saving the transcript and the final diff. Write eval/score.py: per run, check the transcript and repository state for each targeted rule (ran the right test command, wrote a plan before edits, added a failing test before the fix, claimed done only after verification). Output a table of adherence per rule per arm.

Expect: eval/ tasks, runner, scorer, raw results and an adherence table.

Audit before moving on: Hand-check 5 random scored runs against their transcripts; any scorer mistake is fixed and all runs re-scored. If a task is followed 100% even with no file, it is too easy; replace it.

Step 6 — Validate against oracles and write the gap report

Goal: Decide what to keep, what to delete, and what is still unknown.

Compare adherence per rule across the three arms. A rule that shows no improvement over no file is a deletion candidate unless it encodes a project fact.

Confirm each hook blocks its violation live and passes its tests.

Re-measure final line and token counts.

Ask a teammate, or yourself over the next week, to log any correction they still have to give; list the plan for that log.

Write report.md: adherence table, rules to delete, hooks added, token weight, claims verdicts.

Write gaps.md: unverified loading claims, rules not scorable automatically, run-to-run variance, conflicts with the global CLAUDE.md, and anything skipped. Fix what you can now.

Add a dated line to the file's history or a lessons file recording this eval's result, so the next rebuild starts from measured adherence instead of memory.

Expect: report.md, gaps.md, final CLAUDE.md committed with its eval results.

Audit before moving on: Re-run the eval for the new file once more and confirm adherence is within the earlier run-to-run range. Confirm no secret or personal data from transcripts was copied into any output.

6 · Failure modes

Cargo-cult rules. Tell: rules nobody can tie to an incident. Fix: require a reason per rule and delete the rest.

Prose for walls. Tell: an absolute rule broken despite being in the file. Fix: hook or permission deny with a test.

Bloat. Tell: file grows past 200 lines and key rules get ignored. Fix: move details to linked docs and hooks, keep the top tight.

Stale commands. Tell: Claude runs a test command that no longer exists. Fix: verify commands from config each time the file changes.

Unmeasured improvement. Tell: 'it feels better'. Fix: run the headless eval with three arms and repeats.

Outdated mechanics. Tell: relying on a shortcut or loading path the current version changed. Fix: check docs for the installed version.

Transcript leakage. Tell: secrets or personal text copied into corrections.md. Fix: quote only the gist and scrub before committing.
