Skills That Earn Their Lines — benchmark-gated self-editing plus subtraction

Insight class: Workflow Multiplier · Difficulty: Medium · Quality: 5/5 Connected entries: 11 · Tools: Anthropic, Antidoom, ChatGPT, Claude, Claude Code, Grokbot, OpenAI, Prime Agent, SkillOpt, Soup

Thesis

Successor to the harness and second-brain dives. Those stop at 'append a lesson after every mistake'. The catalog now holds the missing machinery — Microsoft SkillOpt rewrites skills only when a benchmark improves, bilevel autoresearch adds a coach loop over the worker, Prime Agent rewrites its own harness to 95.5% on ARC-AGI-3 — and, crucially, evidence that subtraction matters as much as addition: Boris Cherny's simple mode and the setup-purge post show stale rules make newer models dumber. Combine them into a ratchet that both adds and deletes rules, keeping only edits that beat a held-out eval.

Why it matters

Every power user's CLAUDE.md grows monotonically until it is a tax on every call. A two-way, eval-gated ratchet turns rule accretion into measured improvement, and the winning traces become fine-tuning data you can push into a small local model with Soup.

3 · Step-by-step prompts

Step 1 — Build the held-out eval from history

Goal: Turn exported chat history into an objective eval with a cheap model.

Establish the oracle. Export the chat history (angus.sewell's point: it is the best personalization dataset). Have a cheap or local model (Haiku-class) tag ~40 representative tasks from it, each with an objective pass/fail criterion a human could apply (not 'good' - e.g. 'produced valid JSON', 'followed the plan-first rule', 'refused unsafe action'). Make this a held-out set never used to tune rules. Build a runner that scores a given CLAUDE.md+skills setup against all ~40 tasks. This eval is what every ablation and every optimizer edit is judged against; a change that does not move it does not merge.

Expect: ~40 held-out tasks tagged with objective pass/fail criteria, plus a runner that scores a setup against them.

Audit before moving on: Check 5 criteria are objective enough for two graders to agree, and that the tasks span real usage (not just easy ones). Fail if criteria are subjective or the set is cherry-picked. On fail, re-tag with tighter criteria.

Step 2 — Noise floor + falsifier

Goal: Prove the eval is signal before building the ratchet on it.

Answer the dive's falsifier before anything else. Run the SAME setup against the eval 2-3 times and measure the variance between runs - this is the noise floor. Then estimate the gap you expect between the best and worst rule sets. If run-to-run variance is comparable to or larger than that best-vs-worst gap, STOP and report that the eval is too noisy and the whole ratchet would be optimizing noise; enlarge the eval or tighten criteria until variance is clearly below the gains you need to detect. Only proceed past this step if the noise floor is small enough to trust.

Expect: A measured run-to-run variance, a stated expected best-vs-worst gap, and a go/no-go verdict on the eval's trustworthiness.

Audit before moving on: Confirm the repeated runs used identical config. Fail if you proceed while variance rivals the expected gains. On fail, enlarge/tighten the eval before building the ratchet.

Step 3 — Ablation sweep (the subtraction half)

Goal: Delete rules and skills whose removal does not hurt the eval.

Run the subtraction half of the ratchet (cooper.simson's purge; Cherny's simple mode). Drop each CLAUDE.md rule and each skill ONE AT A TIME, re-run the eval, and record the score without it. Delete anything whose removal does not drop the score beyond the step-2 noise floor - EXCEPT safety/money/security rules, which are never deleted regardless of eval. Produce an ablation table: item, score with, score without, delta, deleted/kept/locked. The goal is the smallest rule set that holds the score; stale rules written for older models are the primary target.

Expect: An ablation table over every rule and skill, with deletions made for items whose removal did not hurt beyond noise, safety rules marked locked.

Audit before moving on: Confirm each deletion was decided by a real re-run and the delta is within noise. Confirm no safety/money rule was deleted. Fail if nothing was deleted (no real ablation) or a guardrail was cut. On fail, run the ablations properly and restore any guardrail.

Step 4 — SkillOpt-style gated optimizer

Goal: Add edits only when they beat the benchmark; reject the rest.

Build the addition half as a SkillOpt-style loop (github.com/microsoft/SkillOpt): (1) skills log their own failure notes as they run (angus.sewell's issues-table pattern). (2) An optimizer reads the notes and the eval failures and proposes an edit to a rule or skill. (3) The edit is applied to a copy, the eval is re-run, and the edit MERGES only if it beats the current benchmark beyond the noise floor; otherwise it is auto-rejected (SkillOpt's core behaviour). Isolate successful paths from failures. Put the loop on a nightly cron. Log every proposed edit with its before/after score and the merge/reject decision. Never let the optimizer touch the locked safety set.

Expect: A gated optimizer loop (log notes -> propose -> eval -> merge only if it beats baseline beyond noise) on a nightly cron, with an edit log and the safety set excluded.

Audit before moving on: Inspect the edit log: confirm every MERGED edit beat baseline beyond noise and every rejected one did not, and that no edit touched the locked set. Fail if a non-improving edit merged or a safety rule was edited. On fail, fix the gate threshold and the exclusion.

Step 5 — Bilevel outer loop + lock safety

Goal: Revise the optimizer's strategy, and make risk rules uneditable.

Add the two robustness pieces. (1) Bilevel outer loop (raycfu): wrap the SkillOpt loop with an outer loop that periodically revises the OPTIMIZER'S strategy - what kinds of edits it proposes - not just the skill text, so it does not keep trying the same few instincts (raycfu: single loops collapse onto a few favourite ideas). Measure whether the bilevel version explores more distinct edit types than the single loop. (2) Lock the safety set: move all safety/money/security/risk rules into a file or section the loop reads but cannot modify, enforced in code (raycfu's hard-coded-risk-limits pattern). Confirm the optimizer cannot write to it.

Expect: A bilevel outer loop shown to diversify edit types, and a code-enforced lock on the safety/risk rule set.

Audit before moving on: Compare edit-type diversity with and without the outer loop; confirm the optimizer physically cannot modify the locked file. Fail if the outer loop just re-runs the same edits or the safety file is writable by the loop. On fail, fix the strategy-revision step or the lock.

Step 6 — Validate, export traces, gap report

Goal: Prove the ratchet beats baseline beyond noise; export winners; report honestly.

Final validation. (1) Run the final ratcheted CLAUDE.md+skills against the held-out eval vs the starting set; report the gain and confirm it exceeds the step-2 noise floor. Apply wassimyounes_'s caveat: a sub-noise margin is NOT an improvement - say so if that is the case. (2) Export the passing traces (the task runs the winning rule set got right) in a format suitable for a Soup (martintrainhard) small-model fine-tune, and note whether a fine-tune is worthwhile. (3) Enumerate claims, mark verified/unverified/false, list missing pieces ranked by impact, fix the top two. Commit the eval, harness, and ratcheted setup; print the hash.

Expect: A final-vs-baseline eval comparison with a gain exceeding noise (or an honest null result), an exported passing-trace set for Soup, a claim ledger, and a committed setup with hash.

Audit before moving on: Confirm the final gain exceeds the noise floor; if not, state plainly the ratchet did not beat baseline. Confirm the exported traces are the passing ones, not all runs. Fail if a within-noise margin is reported as a win. On fail, report the null result honestly.

4 · Gap analysis and audit

Run this after the build. It makes the agent enumerate its own claims, mark what is verified, rank the gaps and fix the top ones.

Run after the ratchet is built. Enumerate every claim as a numbered list: the eval's objectivity and representativeness, the noise floor, each ablation deletion and keep, each merged/rejected optimizer edit, the bilevel loop's added diversity, the safety lock, and the final gain. Mark each VERIFIED (with run numbers), UNVERIFIED, or FALSE. Specifically re-check: were the eval criteria objective and the set truly held out; is the noise floor below the gains claimed (the falsifier); did the ablation actually DELETE rules, or only keep; did every merged edit beat baseline beyond noise and every rejected one fail; is any final gain within the noise band (a 0.1%-style non-result); is the safety/risk set genuinely uneditable by the loop; are the exported traces the passing ones. Fix the top three and re-verify. Report what you could not fix and why. Do not report any improvement that is within the noise floor as a win.

5 · What proves it right

On the held-out eval, the ratcheted rule set beats the starting set by more than the measured run-to-run variance (or the result is honestly reported as null).

The ablation table shows specific rules deleted because their removal did not hurt the eval, and kept rules each hurt when removed - proving two-way, not monotonic, change.

Every merged optimizer edit beat the benchmark beyond noise and every rejected edit did not, per the edit log (SkillOpt's gating behaviour).

The safety/money/risk rule set is provably uneditable by the loop (an attempted write is blocked in code).

The noise-floor check answers the falsifier: run-to-run variance is below the best-vs-worst rule-set gap, or the eval is declared too noisy to trust.

6 · Failure modes

Monotonic ratchet: only adds, never deletes. Tell: CLAUDE.md keeps growing, no ablation deletions. Fix: run the ablation sweep and delete what removal does not hurt.

Optimizing noise: eval variance rivals the gains. Tell: results flip between identical runs. Fix: measure the noise floor first; enlarge/tighten the eval (the falsifier).

Ungated merges: edits applied without beating the benchmark. Tell: edit log has merges with no positive delta. Fix: enforce SkillOpt's merge-only-if-better gate beyond noise.

Editable safety rules: the loop rewrites risk limits. Tell: a guardrail changed after a run. Fix: lock safety/money rules in a code-enforced uneditable set.

Tuning on the held-out set: eval used to drive edits. Tell: great eval, worse real behaviour. Fix: keep a sealed set never used for tuning.

Collapsed bilevel loop: outer loop re-runs the same instincts. Tell: low edit-type diversity. Fix: make the outer loop revise the optimizer's strategy, measure diversity.

Sub-noise 'win': a 0.1%-style margin claimed as improvement (Prime Agent caveat). Tell: gain within variance. Fix: require the gain to exceed the noise floor; else report null.
