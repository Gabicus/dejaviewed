One-line framing. llms.txt is the file you put at the root of your website so that LLM agents — Claude, ChatGPT, Perplexity, Cursor, Gemini, whatever — can figure out what your site is and what matters on it without having to crawl, render, and guess from the HTML. It's the "manifest" layer for AI-era web discovery, sitting next to robots.txt and sitemap.xml but aimed at a different reader.

What it is

llms.txt is a proposed standard, introduced by Jeremy Howard (fast.ai / Answer.AI) in September 2024, for a single Markdown file hosted at the root of a website that gives large language models a compact, structured, high-signal overview of the site. The format is unusual in one important way: it uses Markdown, not XML or JSON, specifically because the consumer is a language model that already parses Markdown natively and benefits from prose context around link lists.

There are two companion artifacts:

  1. /llms.txt — the short, curated index. Think of it as "here is what this site is, and here are pointers to the dozen or so pages that actually matter." This file is meant to fit comfortably in a model's context window.
  2. /llms-full.txt — an optional, much longer file (co-developed by Mintlify and Anthropic) that inlines the full Markdown of every important page in one document. Useful when you want an agent to have the entire docs corpus in a single fetch without walking links.

Both live at predictable, fixed paths at the domain root. There is no registration, no API, no keys. It is a web standard in the Robots Exclusion Protocol tradition: just drop a file, and the agents that care will find it.

How it differs from existing web metadata files

File Primary reader Purpose Format
robots.txt Crawlers Tell bots where they may and may not go Line-based directives
sitemap.xml Search engines List every URL for exhaustive indexing XML
humans.txt Humans Credit the team behind a site Free-form text
llms.txt LLM agents Explain what the site is and which pages carry the meaning Markdown
llms-full.txt LLM agents Inline full content of key pages in one doc Markdown

The critical distinction is curation vs. exhaustiveness. A sitemap is a phonebook: every URL, flat, no commentary. llms.txt is an index card on the front of the site that says "here is what we do, and here are the ten links an agent should read first." Search engines can afford to crawl 50,000 URLs; an LLM agent answering a user question has a 200k-token budget and 3 seconds. The whole point is to make the agent's first fetch the one that actually matters.

robots.txt governs access. llms.txt governs attention. They are complementary, not competing.

How it works

The spec, condensed

The format is deliberately minimal. The only hard requirement is a single H1 at the top. Everything else is recommended but optional.

# Project or Site Name

> Optional one-paragraph description as a Markdown blockquote. This is the
> "elevator pitch" the model will read first. Keep it tight — one or two
> sentences that a model can use as a summary when someone asks "what is
> this site?"

Optional free-form Markdown prose giving extra context: who runs the site,
what it's for, any important caveats, how the content is organized. You
can link freely; links here are treated as inline references.

## Docs

- [Getting Started](https://example.com/docs/getting-started): One-line description of what this page covers.
- [API Reference](https://example.com/docs/api): The full REST API.
- [CLI Guide](https://example.com/docs/cli): Command-line usage.

## Examples

- [Tutorial: Hello World](https://example.com/examples/hello): Minimal walkthrough.
- [Cookbook](https://example.com/examples/cookbook): Common recipes.

## Optional

- [Changelog](https://example.com/changelog): Release history.
- [Blog](https://example.com/blog): Long-form writing.

Rules of the road:

  • H1 is required. It's the name of the site/project. Exactly one.
  • Blockquote is the summary. If present, it goes immediately after the H1, and it's the single most important piece of metadata.
  • H2 sections group links. Common section names in the wild: Docs, Examples, API, Guides, Blog, Policies, Optional.
  • Each link is a bullet of the form [Title](URL): one-line description. The description is what the model uses to decide whether to fetch the link.
  • An ## Optional section is treated as lower priority. Models that are context-constrained may skip it entirely. Use it for "nice to have but not load-bearing" links.
  • All URLs should be absolute (full https://...), not relative, because agents may fetch this file from cache or a mirror.

That's the whole spec. No versioning headers, no front-matter, no required metadata fields. Plain Markdown a human can hand-write in five minutes.

The llms-full.txt variant

llms-full.txt takes every page in your "Docs" section (or whatever you consider canonical) and concatenates the raw Markdown of each page into one file, with ## Page Title headers separating them. The goal is "single fetch, full context." This was co-developed by Mintlify and Anthropic and is now part of the broader proposal. Anthropic, Stripe, Vercel, Cursor, Cloudflare, Pinecone, and Windsurf all publish one.

Rule of thumb:

  • llms.txt → index of pointers, always ship this.
  • llms-full.txt → inlined body, ship this if your docs are < ~500k tokens and you want agents to have one-shot access.

Companion: .md versions of every page

The third leg of the proposal is that every HTML page should also be served as a plain Markdown version at the same URL with a .md suffix (e.g., example.com/docs/api → example.com/docs/api.md). This is what nbdev, Mintlify, Fern, and a growing number of docs platforms now do automatically. It lets an agent fetch a clean, parser-friendly version of any page linked from llms.txt without having to scrape HTML. Fern goes a step further and detects LLM bot user-agents and serves the Markdown version directly at the original URL, claiming a 90%+ token reduction versus rendered HTML.

Key mechanics

Who's adopted it

As of late 2025, real llms.txt files in production include:

  • Anthropic (docs.anthropic.com/llms.txt) — the flagship reference implementation, co-developed with Mintlify.
  • Stripe, Cloudflare, Vercel, Supabase — canonical dev-tool adopters.
  • Cursor, Windsurf — AI-native IDEs that both publish and consume.
  • Pinecone, Coinbase, Mintlify, Perplexity — AI infra and docs-heavy companies.
  • Every site hosted by Mintlify, Fern, Docusaurus (via plugin), GitBook, and several other docs platforms — these auto-generate llms.txt and llms-full.txt on build, which is how adoption jumped from "a handful of early movers" to ~844k sites in under 12 months.

Notable non-adopters: most CMS-based marketing sites, most WordPress blogs, and most e-commerce storefronts. The long tail is still wide open.

Who reads it

Consumption is less well-documented than publication, but in practice:

  • Cursor, Windsurf, Claude Code, Continue, Aider — when pointed at a library, many will check /llms.txt before crawling the docs site.
  • Perplexity and ChatGPT's browsing/search modes — will opportunistically read llms.txt when building a retrieval plan.
  • Agent frameworks (LangChain, LlamaIndex, Mastra, CrewAI) — have helpers/loaders for fetching llms-full.txt as a one-shot document source.
  • Claude's WebFetch tool — does not yet auto-prefer llms.txt, but will honor it if you instruct the agent to check.

The honest state of the world: publication is ahead of consumption. Shipping llms.txt today is primarily a bet on the near-future agent web, plus a free SEO/GEO (Generative Engine Optimization) signal that costs 30 minutes to put in place.

Tools that generate it

  • Mintlify — auto-generates /llms.txt, /llms-full.txt, and .md versions of every page for all hosted docs. Zero config.
  • Fern — same, plus the bot-detection serve-Markdown-at-original-URL trick.
  • llmstxt npm / Python packages — scrape a sitemap and produce a draft llms.txt you can hand-edit.
  • llmstxtgenerator.org, seomator.com, Mintlify's free generator — web-based form-fill tools for non-technical site owners.
  • Docusaurus plugin @signalwire/docusaurus-plugin-llms-txt, Nextra, Astro Starlight — framework-level plugins that generate the file at build time from your existing docs tree.
  • Hand-written — for a portfolio site, just write it. It's a 30-line Markdown file.

Quick start

1. Publish the simplest possible version (5 minutes)

Write this file, save it as llms.txt, put it at the root of your site so it's served at https://yourdomain.com/llms.txt, and deploy:

# Your Site Name

> One-sentence description of what this site is and who runs it.

## Main pages

- [About](https://yourdomain.com/about): Who I am and what I do.
- [Work](https://yourdomain.com/work): Portfolio of projects.
- [Contact](https://yourdomain.com/contact): How to reach me.

That's it. You now have a valid llms.txt.

2. Verify it's reachable

curl -I https://yourdomain.com/llms.txt     # expect 200 OK, text/plain or text/markdown
curl    https://yourdomain.com/llms.txt     # sanity check the body

Make sure robots.txt does not disallow /llms.txt for the bots you want to read it. Most agent user-agents ignore robots.txt entirely, but the file should be allowed for completeness.

3. Add llms-full.txt if your site has real written content

If you have a blog, essays, or docs totaling under ~500k tokens, generate a concatenated llms-full.txt and ship it too.

4. Add .md twins for key pages

If you control the rendering layer, serve a .md version of each canonical page at the same URL + .md suffix. In Next.js, this is a middleware rewrite plus a Markdown serializer. In a static site, it's a build step.

Sample: a working llms.txt for 1gabe.com

Here is a complete, ready-to-ship sample for your portfolio site. Drop it at https://example.com/llms.txt, edit the link list to match the actual page structure, and you're done.

# 1gabe — the user

> Portfolio, experiments, and field notes from the user: creative
> technologist working at the intersection of AI, design engineering, and
> algorithmic trading. Based in the US.

This site is a living portfolio. It collects production work (web and
product), independent research (mostly AI and quantitative trading),
writing, and selected visual / generative experiments. Everything is
hand-built; there is no CMS. If you are an agent trying to understand
what you do and what to link to when someone asks about him, start
with the About page and the Work index.

## About

- [About](https://example.com/about): Bio, background, current focus, and contact details.
- [Now](https://example.com/now): What you are actively working on this month.
- [Uses](https://example.com/uses): Hardware, software, and tooling stack.

## Work

- [Work Index](https://example.com/work): Chronological portfolio of shipped projects.

- [Trading Agent Team](https://example.com/work/trading-agent-team): Multi-agent crypto research system with graduated take-profit and ensemble strategies.
- [AI Catalogs](https://example.com/work/ai-catalogs): Curated deep-dive guides on AI tools, repos, and techniques.

## Writing

## Experiments

- [Experiments Index](https://example.com/experiments): Generative, creative-coding, and interactive prototypes.

## Contact

## Optional

- [Colophon](https://example.com/colophon): How this site is built.
- [RSS](https://example.com/feed.xml): Writing feed.

Notes on this sample:

  • The blockquote is the single highest-leverage piece of text in the whole file. It should read like a one-sentence answer to "who is this person?" — because that is literally how a model will use it.
  • The short prose paragraph after the blockquote is optional but valuable for a portfolio. It tells the agent how to think about the site before it starts fetching links. Models that respect this guidance produce dramatically better answers when someone asks "what does you do?"
  • Each link description is a single phrase. Resist the urge to write full sentences — the model will read the destination page for detail.
  • Work, Writing, Experiments, Contact are in the main body. Archive, Colophon, and RSS are under ## Optional so context-constrained agents know they can skip them.
  • If 1gabe.com ever hits a point where the written content is substantial, add a companion llms-full.txt that inlines the body of About, Now, and every entry under Writing.

What we could build with it

  • Auto-generator for your sites. A small Node or Python script that walks 1gabe.com and wv-art.com, reads the existing site map and page titles, and produces a draft llms.txt the first time, then keeps it in sync on every deploy. Wire it into the build step.
  • Claude Code / Cursor skill: "add llms.txt to this project." A skill that detects the framework (Next, Astro, Docusaurus, Mintlify, Hugo, raw static), picks the right generation path, and drops a ready-to-edit draft at the right location.
  • Portfolio-specific template library. you could publish a small set of opinionated llms.txt templates for portfolio sites, art sites, and small-studio sites — the format is still dominated by dev-tool docs, and the creative / portfolio corner of the spec is underserved.
  • Audit tool. A CLI that fetches a site's llms.txt, validates it against the (loose) spec, checks that every link resolves, measures total token count, and flags missing .md twins. Good companion to existing SEO auditors.
  • llms-full.txt inliner with smart truncation. For sites that are too big to inline everything, a tool that uses embedding similarity to pick the N most semantically "central" pages and inlines only those, within a configurable token budget.
  • GEO reporting dashboard. Track which agents actually fetch your /llms.txt by user-agent and log it. Useful signal for whether the investment is paying off.
  • Integration with the AI catalog itself. Ship an llms.txt for this ai-catalogs repo so that other agents discovering it can get an indexed view of every guide. A natural fit — each guide here already follows a consistent pattern.

1 · Deeper, not bigger

Before running anything, make the task deeper rather than larger. Ask: what would a top professional do here that I am not asking for; what is the rawest material; which methods and tools; what, other than the model or me, proves it right. Then ask for exactly that.

  • What a top professional would do (that you didn't ask for): A docs or growth engineer would treat llms.txt as a build artifact, not a hand-edited file, generated from the same source of truth as the sitemap so it cannot rot. They would measure the real benefit: token cost per page as HTML versus Markdown, and answer accuracy on a fixed question set with and without the file. They would also be honest that publication is ahead of consumption, so they would instrument access logs for agent user agents (GPTBot, ClaudeBot, Claude-User, PerplexityBot, ChatGPT-User, and others) before claiming anyone reads it, and keep robots.txt policy consistent with what llms.txt invites.
  • Rawest material to start from: The spec at llmstxt.org and Jeremy Howard's proposal post (answer.ai/posts/2024-09-03-llmstxt.html); the reference repo github.com/AnswerDotAI/llms-txt with its parser and the llms_txt2ctx CLI; real production files to compare against (docs.anthropic.com/llms.txt and llms-full.txt, Stripe, Cloudflare, Vercel); your site's own sitemap.xml, build output directory, and source content (Markdown, MDX, or CMS export); your host's raw access logs (Cloudflare logs or analytics, nginx access.log); and the published user-agent strings for each AI crawler from the vendors' own docs.
  • Methods and tools: pip install llms-txt and use its parse function and llms_txt2ctx to validate structure and expand the context file; a build script (Python or Node) that reads the sitemap or content tree and emits llms.txt, llms-full.txt, and per-page .md files; html-to-markdown conversion with a readability step (for example trafilatura or defuddle) when source Markdown is unavailable; tiktoken or the Anthropic token-counting endpoint for sizes; lychee for link checking; curl -I for status and Content-Type (text/plain or text/markdown, UTF-8); an evaluation set of 15-20 site questions answered by Claude, ChatGPT, and Perplexity with and without being pointed to /llms.txt.
  • What proves it right (other than you or the model): Oracles beyond the model: (a) the AnswerDotAI llms-txt parser loads the file and returns the expected title, summary, and sections; (b) lychee reports zero broken links in llms.txt and llms-full.txt; (c) curl shows 200 and a text content type for /llms.txt, /llms-full.txt, and every .md twin; (d) access logs show which AI user agents fetched the files and how often over two weeks; (e) the question-set accuracy with versus without llms.txt, graded against answers written from the site before testing.

2 · One-shot prompt

ROLE AND STANCE
You are a docs and web-platform engineer adding the llms.txt layer to one real site so agents can understand it from a single fetch. You make it a generated build artifact, validate it with the reference parser, and measure whether it changes anything. You do not overclaim adoption by readers.

CONTEXT
- Spec (llmstxt.org, proposed by Jeremy Howard, Answer.AI, September 2024): Markdown file at /llms.txt. Exactly one H1 (required). Optional blockquote summary immediately after. Optional prose. H2 sections containing bullets of the form [Title](URL): description. A section named Optional is lower priority and may be skipped by context-limited agents. Use absolute URLs.
- Companions: /llms-full.txt (concatenated Markdown of canonical pages, co-developed by Mintlify and Anthropic; ship if under ~500k tokens), and .md twins at page URL + .md.
- Reference implementation: github.com/AnswerDotAI/llms-txt (Python parser, llms_txt2ctx CLI). Real examples: docs.anthropic.com/llms.txt and llms-full.txt; Stripe, Cloudflare, Vercel, Supabase.
- Generators: Mintlify and Fern (automatic), Docusaurus plugin @signalwire/docusaurus-plugin-llms-txt, Nextra, Astro Starlight plugins, llmstxt npm and Python packages.
- Claims to TEST: ~844,000 sites have adopted it (BuiltWith, October 2025); Fern's Markdown serving cuts tokens by 90 percent or more versus HTML; Cursor, Windsurf, Claude Code, Aider check /llms.txt; Claude's WebFetch does not auto-prefer it; publication is ahead of consumption.

HARD CONSTRAINTS
- Generate the files from the site's source or sitemap in the build; no hand-maintained copy that can drift.
- Absolute https URLs only. Every linked URL must return 200.
- Serve with a text content type and UTF-8; do not let the host serve it as HTML or force a download.
- Keep robots.txt consistent: do not invite agents in llms.txt to paths robots.txt disallows for them, and do not change robots.txt policy without the user's decision.
- Do not include private, draft, or unlisted pages.

ORDERED DELIVERABLES
1. ground-truth.md: the spec rules in a checklist, the parser's behaviour on docs.anthropic.com/llms.txt, current adoption evidence you can find with sources, and verdicts on the claims above where checkable.
2. inventory.csv: every page from sitemap.xml with URL, title, word count, include (core, optional, exclude), and a draft one-line description.
3. scripts/build_llms.(py|mjs): emits dist/llms.txt, dist/llms-full.txt, and dist/<path>.md twins from source Markdown (or from built HTML via trafilatura/defuddle if no source Markdown exists); wired into the existing build command.
4. The generated files, with the blockquote written as a one-sentence answer to 'what is this site and who runs it'.
5. Host config for content types and .md routes (for example a _headers file on Cloudflare Pages, nginx types, or a Next.js route).
6. validation.md: parser output, llms_txt2ctx output size, lychee report, curl -I results for every file, token counts per page in HTML versus Markdown.
7. eval/questions.csv: 15-20 site questions with reference answers written before testing; results per agent (Claude, ChatGPT, Perplexity) with and without the llms.txt pointer; correct y/n.
8. logs/agent-ua.sql or script: query for AI user agents hitting /llms.txt, /llms-full.txt, and .md twins; a reminder to re-run after 14 days.

BUILT-IN GAP ANALYSIS
Before finishing, write gaps.md: pages excluded and why; pages whose Markdown conversion lost content (tables, code blocks, images with meaning); claims you could not verify (adoption count, which agents read the file); whether the eval shows a real accuracy gain or just noise at this sample size; whether the build fails loudly if a listed page disappears. Fix what you can now (for example add a build assertion that every llms.txt link exists in the sitemap).

SELF-QUESTIONS BEFORE FINISHING
- Does the file have exactly one H1, and does the parser read my sections as intended?
- Would a model reading only the blockquote answer 'what is this site' correctly?
- Is each description specific enough for a model to decide whether to fetch the link?
- Are .md twins faithful, including code blocks and tables?
- Is llms-full.txt under the size where a model can actually load it, and did I measure tokens?
- What happens to llms.txt when a page is renamed: does the build fail or silently ship a dead link?
- Do robots.txt rules and llms.txt invitations agree for each AI user agent?

STOP CONDITIONS
Stop when the files are deployed, validated, and the eval is graded; leave the log check scheduled. Stop and ask before changing robots.txt policy, before including any page that requires login, or if the host cannot serve text content types without a plan change.

RETURN FORMAT
One message: the final llms.txt content in a code block; file list; validation summary (parser ok, broken links, content types); token table (page, HTML tokens, Markdown tokens, reduction percent); eval table (agent, with, without); claims verdicts; gaps.md contents; the date to re-run the log query.

Step 1 — Ground truth: spec, reference parser, real examples

Goal: Know the real rules and how the reference tooling reads a file before writing one.

Fetch docs.anthropic.com/llms.txt and two other production files (for example Stripe and Cloudflare); run the parser on each and record what it extracts (title, summary, info, sections and link counts). Search vendor documentation for which AI agents document fetching llms.txt. Write ground-truth.md with the checklist, the parser results table, and claim verdicts (verified, contradicted, unverified).

Expect: ground-truth.md with a 7-10 item checklist, a parser results table for 3 real files, and verdicts on the 5 guide claims.

Audit before moving on: If the parser rejects or misreads a real production file, note it; that tells you how strict validation is. Every verdict must cite a URL. Claims with only blog-post support are 'unverified', not 'verified'.

Step 2 — Inventory the site and choose what matters

Goal: Decide which pages carry the site's meaning and write model-facing descriptions.

Fetch <domain>/sitemap.xml (or read the build output directory if there is no sitemap) and list every URL in inventory.csv with title, word count from the built HTML, and last modified. Mark each page core, optional, or exclude: core pages answer who, what, and how to use the site; optional pages are useful but not load-bearing (archives, changelogs, colophon); exclude drafts, tag pages, paginated listings, login-gated pages, and near-duplicates. Aim for 10-25 core links. For each included page, write one description of 8-20 words that states what a reader learns there, not marketing copy, and that lets a model decide whether to fetch it. Draft the blockquote: one or two sentences answering 'what is this site and who runs it'. Group core pages into 3-6 H2 sections that match how the site is organized. Check robots.txt and list any included page disallowed for any AI user agent.

Expect: inventory.csv with every sitemap URL and a decision; a draft outline of sections, 10-25 core links, an Optional section, and the blockquote.

Audit before moving on: Read only the blockquote and descriptions and try to answer five basic questions about the site; if you cannot, rewrite them. Any included page that robots.txt disallows is a conflict to resolve with the user, not silently kept.

Step 3 — Generate the files in the build

Goal: Make llms.txt, llms-full.txt, and .md twins build artifacts that cannot drift.

Write scripts/build_llms.py (or .mjs to match the site's tooling). Inputs: inventory.csv decisions plus the site's source Markdown, or built HTML when no source Markdown exists, converted with trafilatura or defuddle and cleaned (keep headings, code blocks, tables, link text; drop nav, footers, cookie banners). Outputs to the build directory: llms.txt with H1 site name, the blockquote, a short prose paragraph, H2 sections with '- [Title](https://absolute/url): description' lines, and '## Optional'; a .md twin at each included page's path + '.md' with a title header and source URL line; llms-full.txt concatenating the core pages' Markdown with '## Page Title' separators and source URLs. Fail the build if any included URL is missing from the sitemap or build output, or if llms-full.txt exceeds a configured token cap (default 400,000 measured with tiktoken). Wire it into the existing build command and add host config so .txt and .md are served as text/plain or text/markdown with charset utf-8 (for example a _headers file for Cloudflare Pages).

Expect: A script under 200 lines, generated files in the build output, and a build log line reporting link count and token totals.

Audit before moving on: Delete one included page from a local build and confirm the build fails with a clear message. Diff three .md twins against their rendered pages and confirm no headings, code blocks, or tables were lost; fix the converter settings if they were.

Step 4 — Validate structure, links, and serving

Goal: Prove the files are conformant and reachable as text.

Run the llms-txt parser on the generated llms.txt and confirm it returns the expected title, summary, and every section with the right link count. Run llms_txt2ctx on it and record output tokens. Run `lychee --no-progress dist/llms.txt dist/llms-full.txt` (or against the deployed URLs after deploy) and require zero broken links. Deploy to a preview environment and run `curl -sI` for /llms.txt, /llms-full.txt, and five .md twins; require HTTP 200 and a text content type with utf-8, no Content-Disposition attachment, and caching headers you intend. Count tokens for each core page as rendered HTML (fetched) and as its .md twin with tiktoken; compute the reduction percent and compare to the guide's cited 90 percent claim. Write validation.md with all outputs and the exact commands used.

Expect: validation.md with parser output, lychee summary (0 errors), a curl table, and a token table per page.

Audit before moving on: Any non-200 or HTML content type is a fail; fix host config and re-test. If the token reduction differs greatly from 90 percent, keep your number and note it; do not adjust the conversion to hit the guide's figure.

Step 5 — Measure agent answer accuracy with and without the file

Goal: Test whether llms.txt changes what agents can answer about the site.

Write eval/questions.csv with 15-20 questions about the site and a reference answer for each, written from the site before any agent testing: who runs it, what it offers, where to find a specific page, a specific fact on a deep page, how to contact, what technology or method a project used. For each agent you can access (Claude with web fetch, ChatGPT with browsing, Perplexity), ask each question twice in fresh sessions: once with only the domain name, once with the instruction 'Read https://<domain>/llms.txt first, then answer'. Record the answer, whether it fetched llms.txt or .md twins (from the agent's citations or your access logs by timestamp), and correct, partial, or wrong against the reference. Compute accuracy per agent per condition.

Expect: eval/questions.csv with reference answers and graded results; a summary table of accuracy per agent with and without the pointer.

Audit before moving on: Confirm reference answers predate the runs (file timestamp or git commit). Use fresh sessions so earlier answers do not leak. If the sample is under 15 questions or differences are within two answers, label the result inconclusive.

Step 6 — Instrument consumption in access logs

Goal: Find out who actually reads the files instead of assuming.

From each vendor's own documentation, collect current user-agent strings for AI crawlers and fetchers (OpenAI GPTBot and ChatGPT-User, Anthropic ClaudeBot and Claude-User, PerplexityBot and Perplexity-User, Google-Extended, and others you find), with source URLs. Write logs/agent-ua.(sql|sh) for the host's logs (Cloudflare Logpush or analytics GraphQL, nginx access.log via awk) that counts requests per user agent for /llms.txt, /llms-full.txt, any .md twin, and the matching HTML pages, per day. Run it now, before deployment, to get a baseline from before deployment if logs exist. Schedule or note a re-run 14 days after deployment, and record the exact command so the numbers are comparable. Compare robots.txt directives for each agent with what llms.txt invites and list mismatches for the user to decide on; do not edit robots.txt yourself.

Expect: A UA list with sources, a runnable log query, a baseline count table, and a re-run date.

Audit before moving on: Test the query on a log line you generate yourself with curl -A 'ClaudeBot' against /llms.txt; it must count it. Verified-bot claims rely on UA strings that can be spoofed; note that in the results.

Step 7 — Validate against oracles and write the gap report

Goal: Consolidate proof and state what is and is not known.

Re-run the parser, lychee, and curl checks against production after deploy. Collect: parser result, broken-link count, content-type table, token table, eval accuracy table, and (when available) the 14-day agent log counts. Write gaps.md with: claims and verdicts (adoption count, token reduction, which agents read llms.txt, WebFetch behaviour, publication ahead of consumption) each with evidence; pages excluded and why; conversion losses found; eval sample size and whether the effect is real; robots.txt mismatches awaiting a decision; the build's drift protection status. Fix the top fixable gap now, without changing reference answers, (for example improve two weak descriptions that caused wrong answers) and redeploy, then rerun the parser. Also check that the build still fails on a missing page. End with the final llms.txt in a code block.

Expect: gaps.md with every claim resolved and a final deployed llms.txt.

Audit before moving on: Every 'verified' must cite a file or log result. If the eval showed no gain, say so plainly and keep the files anyway only if the cost is negligible, stating that reason.

4 · Gap analysis and audit

Run this after the build. It makes the agent enumerate its own claims, mark what is verified, rank the gaps and fix the top ones.

You are auditing an llms.txt rollout on <domain> built by someone else: scripts/build_llms.*, the deployed /llms.txt, /llms-full.txt, .md twins, validation.md, eval/questions.csv, logs/agent-ua.*, gaps.md. Do not trust validation.md. (1) List every claim: spec conformance, link health, content types, token reduction, eval accuracy gain, agent consumption counts, drift protection. (2) Verify each now: run the llms-txt parser against the live file, run lychee against the live URLs, curl -I every file, recount tokens for three pages, rename a page in a local build to test drift protection, and re-grade five eval answers against the reference. Mark verified, unverified, or false with evidence. (3) Look for silent problems: relative URLs, duplicated pages, private or draft pages listed, .md twins missing code blocks or tables, llms-full.txt too large to load, descriptions that are marketing rather than informative, robots.txt contradictions. (4) Check whether the eval was fair (fresh sessions, reference answers written first, same questions). (5) Rank gaps by impact (misleading agents, broken links, exposure of unlisted pages, wasted effort), fix the top three now, redeploy, and report the rest with reproduction steps.

Questions the agent must ask itself before it says done:

  • Does my file have exactly one H1 and a blockquote immediately after it, as the spec requires?
  • Are all URLs absolute https and do they all return 200 with the right content type?
  • Is any page I listed blocked for some AI agent in robots.txt?
  • Would a model reading only my blockquote describe the site correctly?
  • Did .md twins keep code blocks, tables, and meaningful image alt text?
  • How many tokens is llms-full.txt, and can the agents I care about actually load it?
  • Does the build fail if a listed page is removed or renamed?
  • Did any agent actually fetch llms.txt during the eval, and how do I know?

5 · What proves it right

  • The AnswerDotAI llms-txt reference parser loads the live /llms.txt and returns the expected title, summary, and sections.
  • lychee reports zero broken links across llms.txt and llms-full.txt on the deployed site.
  • curl -I on /llms.txt, /llms-full.txt, and each .md twin returns 200 with a text content type and utf-8.
  • Access logs over 14 days, filtered by vendor-documented AI user agents, show who fetched the files.

6 · Failure modes

  • Hand-written file drifts. Tell: dead links months later. Fix: generate in the build and fail on missing pages.
  • Served as HTML or a download. Tell: curl shows text/html or Content-Disposition attachment. Fix: host header rules for .txt and .md.
  • Marketing descriptions. Tell: agents fetch the wrong page or cannot answer basic questions. Fix: rewrite descriptions as what the reader learns there.
  • Relative URLs. Tell: links break when read from a cache or mirror. Fix: absolute https URLs only.

7 · Agent direction (unattended runs)

Read the spec and run the reference parser on real files before writing anything; cache those fetched examples in ground-truth/ so steps do not re-download. Work from the site's own sitemap and source; prefer source Markdown over HTML conversion. Never edit robots.txt or include gated pages without the user's decision. Deploy to a preview first, validate, then production. Spawn a separate subagent to grade eval answers against reference answers so the builder does not grade itself; give it only questions, references, and answers. The 14-day log check needs time: schedule it or leave a dated reminder, do not fabricate counts. Stop and ask if the host cannot set content types or if the site has no reliable page source. Return in chat the final llms.txt, validation summary, token table, eval table, claim verdicts, and gaps; files: ground-truth.md, inventory.csv, scripts/build_llms., host header config, validation.md, eval/questions.csv, logs/agent-ua., gaps.md.
