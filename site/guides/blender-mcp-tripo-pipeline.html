What it is

Blender MCP is a Model Context Protocol server that exposes Blender as a set of tools an LLM can call. You run a tiny socket server inside Blender (via an addon) and an MCP server outside Blender that Claude Desktop, Claude Code, Cursor, or VS Code connects to. From then on, Claude can create objects, apply materials, inspect the scene, run arbitrary Python in Blender's context, pull HDRIs and assets from Poly Haven, and — the reason this guide exists — generate 3D models on demand via Tripo (Hyper3D Rodin) or Hunyuan3D and import them into the current scene.

Combined with Tripo's hosted text-to-3D / image-to-3D API, this turns Claude into a functional 3D scene director. You hand Claude a reference photo, say "build me this scene in Blender and render it from a low angle," and watch it happen. It is the closest thing we have in 2026 to a natural-language Blender operator.

The creator (Siddharth Ahuja / @ahujasid) is an independent developer; this isn't a Blender Foundation or Tripo project. It's the de-facto standard because it went viral on X in early 2025 and everyone built on top of it.

How it works under the hood

There are two processes:

  1. Blender addon (addon.py) — installed inside Blender, runs a Python socket server bound to BLENDER_HOST:BLENDER_PORT (default localhost:9876). When a message arrives, it runs the requested Blender Python API call on the Blender main thread and returns the result.
  2. MCP server (src/blender_mcp/server.py) — a stdio-transport MCP server launched by Claude Desktop / Claude Code. It translates MCP tool calls into socket messages to the addon.

The protocol is simple JSON-over-TCP: a request with type and params, a response with status and result. Because the Blender side runs arbitrary Python, the server is extremely powerful and correspondingly dangerous — save your work before letting an agent drive it.

Tools the server exposes

  • get_scene_info — list objects, cameras, lights, materials
  • get_object_info — detailed info on one object
  • create_object — primitives (cube, sphere, plane, cylinder, etc.)
  • modify_object — transform, scale, rotate
  • delete_object
  • set_material — assign or create a material with base color
  • execute_blender_code — arbitrary Python inside Blender (the escape hatch)
  • get_polyhaven_categories / search_polyhaven_assets / download_polyhaven_asset — free HDRIs, textures, models
  • search_sketchfab_models / download_sketchfab_model — requires API key
  • generate_hyper3d_model_via_text / generate_hyper3d_model_via_images — the Tripo/Rodin integration
  • poll_rodin_job_status / import_generated_asset
  • generate_hunyuan3d_model_via_text / generate_hunyuan3d_model_via_images — local Hunyuan3D-2 bridge

The Hyper3D Rodin endpoint is Tripo's white-labeled API. Blender MCP ships with a free-tier key so you can try it without signing up, rate-limited to a handful of generations per hour. Your own Tripo key removes the limit.

Tripo in one paragraph

Tripo (tripo3d.ai) is the leading hosted text-to-3D / image-to-3D API. Their current model family is P1-20260311 (optimized for clean low-poly output) alongside v3.0 and v3.1 high-detail models. They support text-to-model, image-to-model, and multiview-to-model. Output is GLB with PBR materials, typically 20–60 seconds per generation on their backend. Pricing via fal.ai is roughly $0.20–$0.40 per model; direct Tripo Studio subscriptions start around $10/month for a credit pool. The API is REST: POST a job, poll for status, download the result. Docs at https://platform.tripo3d.ai/docs.

The important thing for this pipeline: Tripo is fast and consistent where Hunyuan3D-2 is slow and local. Use Tripo when iterating on a scene interactively with Claude; use Hunyuan3D-2 (see guides/hunyuan3d-2.md) when you want full local control, custom training data, or no API costs.

System requirements

  • Blender 3.0+ (4.x strongly recommended; 4.2 LTS is the sweet spot)
  • Python 3.10+ (Blender ships its own Python; the MCP server runs in your system Python)
  • uv package manager — mandatory, not optional (install from https://astral.sh/uv)
  • Claude Desktop, Claude Code, Cursor, or VS Code with MCP client support
  • Tripo API key (optional, but required for unrestricted generation) — https://platform.tripo3d.ai
  • Sketchfab API key (optional) for the Sketchfab asset tools
  • Local Hunyuan3D-2 install (optional) if you want local generation — see guides/hunyuan3d-2.md
  • A GPU helps for rendering scenes but is not required for the MCP plumbing itself

No heavyweight ML runs on your machine unless you opt in to Hunyuan3D-2; Tripo and Poly Haven are hosted.

The full pipeline — reference image to rendered scene

Here's the canonical workflow the blender-mcp + Tripo stack enables. Every numbered step is a natural-language turn you'd give Claude in Claude Code:

  1. Drop a reference image in your project (say, a photo of a cozy Japanese tea room)
  2. "Analyze this reference image and list the major 3D objects I'll need to recreate the scene." — Claude reads the image and outputs: tatami floor, low table, tea kettle, shoji screen, hanging lantern, cushion x2.
  3. "For each object in that list, generate it via Tripo image-to-3D using a cropped region of the reference, and import each result into Blender with a sensible name." — Claude loops, calling generate_hyper3d_model_via_images for each object, polling poll_rodin_job_status, then import_generated_asset.
  4. "Lay them out in a plausible room arrangement based on the reference." — Claude calls modify_object to position and rotate.
  5. "Download a warm evening interior HDRI from Poly Haven and set it as the world background." — search_polyhaven_assets → download_polyhaven_asset.
  6. "Add a camera at human eye level, looking at the tea table, and set the Cycles render settings to 512 samples." — via execute_blender_code.
  7. "Render." — via execute_blender_code calling the Blender render operator.
  8. Iterate. Claude can see the result via a screenshot tool and adjust.

The whole loop, end to end, is doable in 5–15 minutes with Tripo on a decent internet connection. The same pipeline with manual Blender work would take a skilled artist hours.

Where it breaks down

  • Object segmentation from a single reference is the weak link. Claude cropping regions of the image is usually "good enough" but precise silhouettes help; feed Claude pre-cropped images for hero assets.
  • Scale. Tripo meshes come in arbitrary units; Claude will fight to normalize them. Tell it "assume 1 Blender unit = 1 meter" up front.
  • Materials. Tripo/Rodin outputs have baked PBR, which is great, but they may not match your scene lighting. Expect a round of set_material tweaks.
  • Topology. These are game-ready but not production film meshes. For feature work, use the new P1 low-poly model and retopologize manually.

Useful prompts to drive it from Claude Code

  • "Inspect the current Blender scene and tell me what's already there."

  • "Here's a photo of my desk (attached). Recreate it in Blender. Use Tripo for any object that isn't a trivial primitive."
  • "Generate a low-poly medieval village: 5 houses, a well, a church, a market stall. Use Tripo's P1 low-poly model. Scatter them on a grass plane with a Poly Haven dawn HDRI."

Claude is surprisingly good at all of these once the MCP connection is live. The bottleneck is your patience and your Tripo quota, not the tooling.

3 · Step-by-step prompts

Step 1 — Ground truth: read the server and vendor docs

Goal: Know what the MCP server really exposes and which vendor generates the models.

Clone github.com/ahujasid/blender-mcp (pull latest if you already cloned it to ./repos/blender-mcp/). Read addon.py and src/blender_mcp/server.py.
1. List every MCP tool with its parameters, the socket host and port, and what each tool sends to the addon. Cite file and line.
2. For the 3D generation tools, find the HTTP endpoints they call and the environment variables they read. Determine whether they call Tripo, Hyper3D Rodin's own vendor, fal.ai, or something else.
3. Check whether a default or free-tier key is embedded, and its stated limits. Do not print key values.
4. Read Tripo's API docs: task creation for image-to-model, polling, output formats, current model version names and prices. Read the Hyper3D Rodin docs to identify its operator.
5. Write tools.md with a verdict on the guide's claims: 'Hyper3D Rodin is Tripo's white-labeled API', 'ships with a free-tier key', 'P1-20260311 model', '0.20-0.40 USD per model via fal.ai'.

Expect: tools.md with cited tool table, provider verdict and claims table.

Audit before moving on: Every tool and provider statement cites a file and line or a doc URL. If Tripo is not wired in, plan a helper for step 4 instead of forcing a mismatched tool.

Step 2 — Install and round-trip

Goal: Get Claude Code talking to Blender reliably.

Install uv. In Blender 4.2 LTS: Edit > Preferences > Add-ons > Install, choose addon.py, enable it, open the BlenderMCP tab in the N-panel and start the server. Configure Claude Code's MCP settings with command uvx, args blender-mcp, and env entries TRIPO_API_KEY and any other provider key, set from your shell environment, not pasted into the config file if your client supports env passthrough.
Restart Claude Code and ask: 'What is in my Blender scene right now?' Confirm get_scene_info returns the default cube, camera and light.
Then test each tool once on a throwaway scene: create a cube, move it, set a material, search Poly Haven for an HDRI, and run execute_blender_code that prints bpy.app.version. Record latency for each call.
Set scene units to metric with unit scale 1.0 and save as template.blend.

Expect: setup.md with config (key names only), a tool test table with latency, template.blend.

Audit before moving on: If any tool call hangs, check the addon is on the main thread and the port matches. Grep the config and logs for key values; any found must be removed and the key rotated.

Step 3 — Camera match and blockout

Goal: Build to the reference camera with primitives before generating anything.

Open the reference photo in fSpy. Mark two vanishing directions along obvious edges (table edges, floor lines) and set a known reference distance, such as a door height or table height. Export and import the fSpy project into Blender with the fSpy importer, giving a camera with matching focal length and pose. Set the reference as the camera background image.
Ask Claude, through the MCP tools, to list the major objects in the photo with an estimated real height in metres for each. Then block out each object with a primitive of that size, placed so it lines up with the photo through the camera view. Name objects clearly (table_low, cushion_left).
Render a quick Eevee preview from the matched camera with 50% opacity overlay of the reference.

Expect: camera/ fSpy files, blockout.blend, overlay preview PNG, objects.csv with names and heights.

Audit before moving on: In the overlay, the blockout's main edges should sit within a few percent of the image width of the photo's edges. If not, redo the fSpy calibration before generating assets.

Step 4 — Generate hero assets

Goal: Generate only objects primitives and libraries cannot cover, with full provenance.

From objects.csv choose at most 8 hero objects. For each, crop the reference tightly around the object, or provide a clean product photo if you have one, and save the crop in assets/crops/.
Call the image-to-3D path verified in step 1: the MCP generation tools if they reach the intended provider, otherwise a small Python helper calling Tripo's REST API with TRIPO_API_KEY from environment (create task, poll, download GLB). Record task ID, model version, start and end time, and cost in provenance.csv.
For anything a Poly Haven model covers adequately, use that instead and record its ID and licence.
Track total spend and stop at 5 USD.
For the first asset, generate twice from the same crop to see run-to-run variation, and once from a text prompt alone, so you know whether image conditioning is worth the cropping effort. Record Tripo's licence terms for generated models in provenance.csv.

Expect: assets/ with GLBs, crops, provenance.csv covering every asset.

Audit before moving on: Every GLB has a provenance row with a task ID. Compare measured generation time and cost with the guide's 20-60 s and 0.20-0.40 USD claims and record the difference in gaps.md.

Step 5 — Import, normalize and audit meshes

Goal: Make every asset scene-ready before placing it.

Save the .blend with a version number. Then, with execute_blender_code, for each GLB: import with bpy.ops.import_scene.gltf, join parts into one object, apply rotation and scale, set origin to the bottom centre, scale uniformly so its height equals objects.csv's real height, and rename it.
Run a bmesh audit per object: vertex and face count, non-manifold edge count, loose vertices, dimensions in metres. Write mesh_audit.csv. Decimate any object above 100k faces to a target you state.
Replace the matching blockout primitive with the asset, copying its location and rotation. Check materials: if baked lighting in the base colour clashes with scene light, reduce it by lowering texture contrast or switching to a neutral material for that object, and log the change. Put all generated assets in a 'generated' collection so they can be hidden for comparison.

Expect: scene_v*.blend files, mesh_audit.csv, a material changes log.

Audit before moving on: All hero assets have applied transforms (scale 1,1,1) and real-world heights within 5%. Any non-manifold count above zero is either fixed or justified in gaps.md.

Step 6 — Light, render, compare

Goal: Produce the final render and measure how close it is.

Use the Poly Haven tools to search and download an HDRI matching the reference's light (time of day, indoor or outdoor, warm or cool) and set it as the world. Add one area light only if the reference has an obvious key light the HDRI lacks.
Set Cycles, 512 samples, OpenImageDenoise, resolution matching the reference aspect ratio, and render from the fSpy camera. Save render.png and scene.blend.
Compare: place reference and render side by side, compute SSIM on downscaled greyscale versions and LPIPS if available. These are rough layout scores, not quality judgments.
Make a second render with the blockout only, and run a blind pick with at least 5 people: show the reference plus the two renders unlabeled, ask which matches better.

Expect: render.png, scene.blend, compare/ with side by side, scores, blind pick results.

Audit before moving on: If the final render loses the blind pick to the blockout, the generated assets hurt the scene; record which ones and why.

Step 7 — Validate against oracles and write the gap report

Goal: Prove the scene is portable and record what remains unverified.

1. Close everything and run blender -b scene.blend -f 1 with Blender 4.2 headless. Confirm the log shows no missing textures, no errors and that the frame was written.
2. Pack external files (File > External Data > Pack Resources) and repeat on a second machine or clean user profile if you can.
3. Reconcile provenance.csv with the provider's own task history.
4. Re-run the mesh audit on the final file.
5. Write gaps.md: each guide claim from tools.md with verified / unverified / false; measured versus claimed speed and cost; assets that needed manual fixes; tools that failed; anything done only through execute_blender_code. Fix what you can now and list the rest.
6. Record total wall-clock time from reference photo to final render and compare it with the guide's '5-15 minutes with Tripo' claim.

Expect: headless_render.log, a packed scene.blend, validation.md, gaps.md.

Audit before moving on: A headless render warning about missing files fails the step until packed. Confirm no API key value appears in the .blend's text blocks, scripts or logs.

5 · What proves it right

6 · Failure modes

  • Wrong provider assumption. Tell: generation tools return errors about keys for a different vendor. Fix: read server.py, then use the right key or a Tripo helper.
  • Scale chaos. Tell: a cup as tall as the table. Fix: metric units first, normalize each asset by real height, apply transforms.
  • Layout drift. Tell: render looks right from nowhere in particular. Fix: fSpy camera match and blockout before generation.
  • Lost work from arbitrary code. Tell: a crashed Blender after execute_blender_code. Fix: versioned saves before each call.
  • Material clash. Tell: objects look pasted in. Fix: reduce baked lighting, match HDRI, use neutral materials where needed.
  • Key leak. Tell: key visible in MCP config or a Blender text block. Fix: environment variables only, rotate any exposed key.
  • Over-generation. Tell: spend climbs on assets nobody sees. Fix: cap at 8 hero assets and 5 USD.

7 · Agent direction (unattended runs)

Start by reading server.py and addon.py; the provider question decides the rest of the pipeline. Cache downloaded GLBs, HDRIs and crops under assets/ so retries do not regenerate or re-bill. Keep Blender operations in the main loop, since they share one scene; a sub-agent may do the fSpy calibration and the vendor-docs reading in parallel. Save a numbered .blend before every execute_blender_code call. Stop and ask before spending past 5 USD, before adding a paid Sketchfab key, and when a provider requires an account the user has not set up. Never print or store key values. If an MCP call hangs twice, restart the addon server rather than retrying blindly. Return README.md linking tools.md, setup.md, camera/, assets/provenance.csv, mesh_audit.csv, scene.blend, render.png, compare/, validation.md and gaps.md, each with a one-line status.
